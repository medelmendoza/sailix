# T0 — Tala API verification results (2026-10-13)

**Authorization (D-T1, recorded verbatim in intent):** the product owner approved a read-only verification against the Tala host `tala-v3-server.btsolve.com` using one dedicated TEST account. The host is the one the shipped Flutter app uses for every request, i.e. **production** (the owner confirmed this explicitly after I pointed it out). Conditions: HTTPS only, read-only, no writes, no production data beyond that account.

**What was run:** `backend/scripts/tala-t0-probe.py` (committed; reads the git-ignored `backend/.env.tala-t0`). 24 authenticated/unauthenticated requests in two runs, 1 per second, plus two unauthenticated `HEAD /` requests and a TLS certificate read earlier. Calls: `POST /api/v1/login` (to obtain a token) and GETs only. **Not called:** register, forgot/change password, delete, team/course apply, progress sync (POST), binary downloads. Output is shape-only: no personal data, ids, tokens or password appear here or in logs.

## Findings

| # | Question | Result | Consequence for M3 |
|---|---|---|---|
| 1 | Is HTTPS available? (D-T2) | **Yes.** HTTP/2, valid Amazon-issued certificate (expires 2027-01-13), `Strict-Transport-Security` header on every response. Plain HTTP *also* answers 200 and does **not** redirect. | Gateway uses `https://` only (already enforced by `TalaEndpointGuard`). The Flutter app's cleartext traffic is an app defect, not a server limit. Recommend the Tala owner redirect/disable HTTP. D-T2 is satisfied **for this host**; it says nothing about other hosts. |
| 2 | Login | `POST /api/v1/login` → `{accessToken, refreshToken, userId}` (as in the source analysis). | Matches the planned adapter. |
| 3 | Token format and lifetime | Both tokens are **JWTs (HS384)**; claims `sub, iat, exp` (+ `authorities` on the access token). **Lifetime ≈ 8,753 h ≈ 365 days for both.** No refresh endpoint was probed (unknown; not guessed on production). | A stolen token is valid for a year → store only encrypted server-side (D-T4/D-T5), never expose to mobile, treat expiry/401 as "relink required" until a refresh endpoint is confirmed. |
| 4 | Identifiers | `userId` is a 40-character string (not a UUID). | Store as opaque string; never trust client-supplied ids. |
| 5 | Teams and roles | The test account belongs to **3 teams**; the profile includes `teamDetails[{teamId, teamName, roleName, teamCode, urpId}]`. **Roles exist server-side** (`roleName`) and the **team join code (`teamCode`) is returned to the client.** | D-T7 (one team per Sailix organization) is workable: verify the mapped `teamId` is among the account's teams on link. **Never forward `teamCode`, `urpId` or `roleName` to the mobile client.** |
| 6 | Server-side authorization of path ids | With the account's own token: a **fake `teamId`** and a **fake `userId`** on the courses endpoint returned **200 with an empty body**, and a fake `userId` on the profile endpoint returned **404** (not 403). | Inconclusive but worrying: the server looks ids up from the path and does not answer 403. Whether another real user's data is readable could **not** be tested (it would need another real id/account, which was not authorized). Assume **no reliable ownership check**: the gateway must build every Tala path only from its own stored link (user id, team id), never from client input. |
| 7 | Error behaviour | No token → **403** (Spring-style `{timestamp,status,error,path}`); malformed token → **500**; unknown user → 404 `{message,httpStatus}`. | Do not treat 403 as "expired"; treat 5xx as upstream failure (retry/backoff), map to `module_unavailable`. |
| 8 | Courses | `GET …/users/{userId}/teams/{teamId}/courses` → assignments with `assignId, courseId, dateFrom/To, status, progress` and `course{courseName, courseDescription, courseThumbnailUrl, totalMaterial, sequential, materialDetails[{materialNum, materialId, materialType, …}]}`. Test account: 2 assigned courses, 18 materials, types **`video`, `pdf`, `up_quiz`** only (no EPUB, legacy quiz or flashcard material on this account). | Read-only course list is straightforward. D-T6 exclusions (legacy QUIZ, EPUB) cannot be exercised with this account; keep them filtered by `materialType`. |
| 9 | Material metadata | Video, PDF and up-quiz metadata endpoints return 200 with JSON including **server-provided file URLs** (`videoFileUrl`, `pdfFileUrl`, thumbnails). Whether those URLs are public/unsigned/expiring was **not tested** (no downloads). | Open: content delivery must be reviewed before streaming through or handing URLs to clients. |
| 10 | **Quiz scoring integrity (D-T8)** | The `up_quiz` payload delivered to the client contains, per question, **`answer`** (and `choices`). Scoring is client-side (source analysis). Progress is pushed with `POST …/courses/sync` (**not tested**: it is a write). | **Confirmed limitation:** the client holds the answer key and computes the score, so a modified client can submit any score. Scores must be shown as **self-reported** unless the Tala backend is shown to re-validate (unknown; needs a write test or the owner's answer). |
| 11 | Stored progress | `GET …/courses/{courseId}/sync/{assignId}/data` returns server-held per-material progress (`materials.{videos,cards,quizzes,epubs,pdfs}`, `progress`, `feedback`, `comment`). | Usable for a read-only progress view. |

## Not verified (needs more authorization or a different account)
Refresh-token endpoint and rotation; whether tokens are revoked on password change; cross-user/cross-team authorization with a real second identity; binary/file URL access control; server-side validation of synced scores; rate limits; wrong-password/inactive-account login responses; EPUB/legacy-quiz/flashcard payloads.

## Security notes about the production service (for the Tala owner, not acted on)
Plain HTTP is accepted without redirect; year-long non-revocable-looking JWTs; garbage bearer token → HTTP 500; ids in paths with 200/empty or 404 instead of 403; join code returned in profile; quiz answer keys sent to clients.

## Addendum (2026-10-13): write verification — owner-authorized, test account only, restored afterwards
Scripts: `backend/scripts/tala-t0-write-probe.py` (T0b), `tala-t0-quiz-shape.py` (T0c, read-only), `tala-t0-quiz-write-probe.py` (T0d, through the real Sailix gateway). The owner explicitly authorized running the write probes on the dedicated test account and a narrow permission rule for exactly those two commands. Output was shape-only; **after every write the account was restored and verified equal to its original state.** 29 requests in total across the runs.

| # | Question | Result |
|---|---|---|
| W1 | Does Tala accept its own stored snapshot posted back unchanged? | **Yes** (HTTP 200 `{message, httpStatus}`); nothing changed afterwards. Extra server metadata fields in the snapshot are tolerated. |
| W2 | Replace or merge? | **Replace.** Adding one row and then posting the original snapshot removed the row again: each POST replaces the whole set of material rows. A client that omits a row deletes it. → the gateway read-modify-writes the full snapshot and keeps every existing row. |
| W3 | Does Tala validate or recompute progress/status? | **No.** What was sent is stored exactly as sent (`progress` string, statuses), and a **decrease is accepted** (the restore did exactly that). The `n/total` counter and every score are whatever the sender says → D-T8 confirmed for the server; the only integrity control is the one the gateway adds (completion never goes backwards, scores computed server-side). |
| W4 | Does Tala accept the exact payload the gateway builds (course-level keep-list, no server metadata)? | **Yes** (video/PDF row, and a quiz row with sections and per-question results). |
| W5 | Quiz encoding | All 30 observed questions are `multipleChoice`, 4 choices separated by `:`, `answer` is a single **0-based index**, `required=true`. Tala's stored quiz row keeps `correct`/`wrong`/`average` as numbers (floats) and `remarks` `PASSED`/`FAILED`. |
| W6 | Concurrency | Not tested against Tala itself. Because POST replaces the snapshot, a write from another client (e.g. the Tala app syncing) between the gateway's read and write would be overwritten (lost update). The gateway's per-link lock only serializes Sailix. |

### Addendum 2 (2026-10-13): flashcards, video feedback and a found defect
Scripts: `tala-t0-cards-shape.py` (read-only), `tala-t0-cards-write-probe.py` (through the real gateway). Same authorization and permission-rule arrangement as above (a third narrow rule was added for the third script).
| # | Finding |
|---|---|
| F1 | The test account's **mapped team has no flashcards**; another team of the same account has one set (`up_card`, 20 cards, picture questions, text answers). Material types seen across the 3 teams: `video`, `pdf`, `up_quiz`, `up_card`. No `card`, `epub` or legacy `quiz`. |
| F2 | Flashcard set document: keys `cardId, cardName, cardDescription, cardThumbnailUrl, cardFileUrl…, tags, data[]`; each card `{tags, question, questionMediaType, questionMediaUploaded, answer, answerMediaType, answerMediaUploaded}` — **no card id** (cards are identified by position). |
| F3 | **`GET …/sync/{assignId}/data` returns 404 for a course the user has never synced.** The gateway treated that as an outage, so the first-ever submission for such a course would have failed with 503. **Defect found and fixed** (404 now means "nothing stored yet"; the course-level record is then built from the assignment). Regression test added. |
| F4 | Tala accepted a complete 20-card set row (counts as numbers, per-card results `EASY`/`MEDIUM`/`HARD`) written through the gateway and stored it as sent. |
| F5 | **Not live-verified:** a video completion with feedback (rating + comment) — the course that had a card set had no video lacking a row. The same fields (`feedback` number, `comment` text) already exist on rows Tala returns, and new-row writes were verified earlier; covered by tests only. |
| F6 | **Residual change on the test account:** that course had no stored record at all, and Tala has no delete, so the probe could only "restore" it to an empty zero-progress record (the course now returns 200 instead of 404). Nothing else on the account differs from before. |
